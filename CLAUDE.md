# Goals — guia para o assistente

App pessoal de acompanhamento (jogos, golos, "estouro", amigos e dívidas) do
pote do Sporting. **Sem build, sem npm.** Site estático (GitHub Pages), PWA.
Dados e login em **Supabase** — o **mesmo projeto do FestasBV**
(`gjweqwfbnkgnibhajldc`), num schema à parte e isolado: `goals`.

## Estrutura
- `index.html` — só markup: layout da app + os três ecrãs de autenticação
  (`page-login`, `page-nova-pass`, `page-sem-acesso`) + o splash de arranque.
- `app.js` — **toda a lógica** (~2750 linhas). Secções (`grep` pelo título,
  não leias o ficheiro todo):
  Sessão Supabase (`sbHeaders`/`sbFetch`/`sbReq`) · Read-only check ·
  **DB** (`carregar`, monta `dbFull`/`db` a partir do Supabase) · Época nav ·
  Cálculos · Nav · Dashboard · **Jogos** · **Pedidos de pagamento** ·
  Golos counter · Modal editar jogo · Amigos · Exportar dívidas ·
  Collapsible sections · Toast · **Estouro dos golos** · Modal add/edit
  estouro · Fab menu · Pote holder · Créditos extra · **Auth (Supabase)** ·
  **Utilizadores ↔ amigos** (admin) · **Migração dos dados antigos** ·
  Logos dos adversários · Init.
- `style.css` — todo o CSS.
- `sw.js` — service worker (cache PWA).
- `db/` — `schema.sql` → `functions.sql` → `policies.sql` (+ `README.md` com
  os passos manuais no painel Supabase). Fonte de verdade do schema `goals`.
- Não mexer: `apple-touch-icon.png`, `manifest.json`, `escudo.png`.

## O modelo em memória não mudou — só a origem dos dados
`dbFull.epocas['2025/26'] = {amigos, jogos, pagosPorJogo, estouros,
estouroPagos, creditosExtra, poteHolder, pedidosPagamento}` continua a ser
exatamente a forma de sempre, e `db` continua o "atalho" para a época ativa
(`sincEpoca()`). O que mudou:
- **`carregar()` é assíncrono** e busca tudo do Supabase (todas as épocas de
  uma vez — o dataset é pequeno, não há paginação por época) em vez de ler
  `localStorage`/GitHub.
- **Não há `salvar()`.** Cada mutação (marcar pago, criar jogo, editar
  estouro, …) faz o `POST`/`PATCH`/`DELETE` **da própria linha** via `sbReq`,
  atualiza o `db` local e re-renderiza — não um "grava tudo em bloco" como
  antes. Se acrescentares um campo editável novo, o padrão é: optimista no
  `db`, `try/catch` à volta do `sbReq`, desfaz o `db` se a rede falhar.
- **Os `id` são reais da BD** (`bigint GENERATED BY DEFAULT AS IDENTITY`,
  lidos de volta com `Prefer: return=representation`), nunca `Date.now()`.
  Exceção: `addAmigo()` dá um id temporário **negativo** a um amigo ainda
  não guardado — `guardarAmigos()` é que faz o `POST` (id<0) ou `PATCH`
  (id>0) de cada um, de propósito, para não disparar um pedido por cada
  tecla do campo de nome/cor.

## Login e permissões (mesmo padrão do FestasBV)
- `SB_URL`/`SB_KEY` são os do projeto partilhado; `Accept-Profile`/
  `Content-Profile: 'goals'` em **todos** os pedidos REST (`sbHeaders`) —
  é isso que aponta para o schema certo, nunca vai no URL.
- **`isReadOnly` já não é "sem token GitHub" — é "não sou admin"**
  (`checkReadOnly` → `isReadOnly = !isAdmin()`). Todo o CSS/`roGuard()` que
  já existia (`.ro-hide`, `body.readonly …`) continua a funcionar sem
  mexer — só a fonte da verdade mudou. `isAdmin()` compara
  `_sbSession.user.email` com `ADMIN_EMAIL` (fixo, o mesmo do FestasBV).
- **Sem conceito de cônjuge/casal** (o Goals não tem isso): um login liga-se
  a **um** amigo via `goals.user_amigos.amigo` (nome, não id — o id de
  `amigos` é por época; o nome é a identidade estável entre épocas).
  `MEU_AMIGO_NOME` guarda esse nome depois do login
  (`sbCarregarMinhaLigacao`); `meuAmigoNaEpoca()` resolve para o `amigo`
  da época ativa, se existir.
- Fluxo de acesso igual ao FestasBV: login → `sbAposLogin` confirma
  `allowed_users` → se não estiver lá, ecrã "sem acesso" com
  "Solicitar acesso" (`access_requests`) → o admin aprova em
  Definições › Utilizadores (`sbRenderPedidos`/`sbAprovarAcesso`).
- **Ligar um login a um amigo é manual, pelo admin** (Definições ›
  Utilizadores › "Ligar"), não há auto-associação por nome parecido.

## Pedidos de pagamento — "já paguei os jogos A, B, D" (`goals.pedidos_pagamento`)
Mesmo padrão do `pagamentos_pendentes` do FestasBV: **pendente não é
dinheiro**. Um amigo (ligado a um login) marca os jogos que já pagou e cria
UM pedido com a lista de `jogo_ids`; fica `pendente` e **não mexe em
`pagosPorJogo`** enquanto o admin não decidir.
- **Lado do membro**: bloco no topo da lista de Jogos (`#meu-pedido-box`,
  `renderMeuPedidoBox`), só visível a quem não é admin e está ligado a um
  amigo da época ativa. Lista os jogos com dívida em aberto **dele**, com
  checkbox; "Já paguei os selecionados" cria o pedido
  (`submeterPedidoPagamento`) e o valor é só informativo (soma calculada no
  cliente). Os pedidos já feitos aparecem por baixo com o estado; enquanto
  `pendente` pode cancelar (`cancelarPedidoPagamento`, `DELETE` — a policy
  só deixa apagar o que ainda não foi aprovado).
- **Lado do admin**: painel no **Resumo**, logo a seguir aos cards
  (`#pedidos-admin-box`, `renderPedidosPagamentoAdmin` — chamado por
  `rResumo()`), só com pendentes da época ativa. **Aprovar** marca primeiro,
  lança depois (`aprovarPedidoPagamento`): `PATCH …&estado=eq.pendente` (a
  trava contra duplo toque/duas sessões) e só depois `POST pagos_jogo` para
  cada jogo do pedido. **Rejeitar** pede o motivo no próprio cartão
  (`mostrarRejPedido`/`rejeitarPedidoPagamento`), nunca `prompt()`.
- Se acrescentares outro sítio que também marca jogos como pagos, os
  pedidos pendentes não têm de aparecer lá — só estes dois blocos.

## Regras técnicas (não partir a app)
- `app.js` carrega como `<script src>` **normal, NÃO module** — há
  `onclick="…"` no HTML, as funções têm de ser **globais**.
- **PWA/cache:** se mexeres em `app.js`, `style.css` ou `index.html`, **sobe
  `CACHE_NAME` no `sw.js`** (ex.: `app-cache-v8` → `v9`).
- **Supabase:** schema `goals`, no mesmo projeto do FestasBV. A chave no
  topo do `app.js` é a **`anon`** (pública, por design), protegida por RLS +
  login. **Não é bug nem risco — não a "corrijas" nem a escondas.**
- **Alterar o schema:** edita primeiro `db/*.sql` (fonte de verdade) e só
  depois corre no SQL Editor do Supabase — nunca ao contrário. Ver
  `db/README.md` para a ordem e os passos manuais (expor o schema `goals`
  na API, redirect URLs, o template de email partilhado com o FestasBV).
- Faz **edições cirúrgicas** (diffs pequenos) — o ficheiro cresceu bastante
  com o Supabase e a auth, mas continua a valer a pena não o reescrever
  todo por um diff pequeno.

## O que já não existe
- **Sync com GitHub** (token, `ghPush`/`ghPull`/`ghAutoPull`, o painel de
  configuração `gh-token`/`gh-owner`/…): removido por completo. Os dados
  já não vivem em `diogoandrefsilva-ghc/AppDataJSON/goals-data.json`.
- **Importar/copiar JSON à mão** (`impJSON`/`lerFich`/`copJSON`): removido
  — não faz sentido com o Supabase como fonte única. Fica só `expJSON`
  (cópia de segurança local, só download).
- O ficheiro `logos.json` desse mesmo repo **continua a ser usado**
  (`carregarLogos`) — são só os escudos dos adversários, não é dado de
  utilizador, não faz parte desta migração.
